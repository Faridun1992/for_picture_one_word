# Архитектура

Статус: архитектура MVP утверждена; базовый мобильный клиент, API каркас и первые таблицы реализованы по TASKS.md.

## Решение по клиенту

Рекомендуемый MVP: отдельный web-first клиент на HTML/CSS/TypeScript (или JavaScript с проверкой типов по мере роста) внутри Capacitor. Не превращать существующий Laravel Blade-сайт в игровую WebView-страницу: мобильный клиент должен быть отдельным приложением с собственными экранами, состоянием и API-клиентом. Это сохраняет навыки владельца и позволяет получить сборки Android/iOS с доступом к native API через плагины.

| Подход | Подходит игре | Сильные стороны | Издержки |
|---|---|---|---|
| Capacitor + HTML/CSS/JS | Игровой цикл — формы, изображения, анимации и простые касания; нагрузки на GPU невысоки | Максимально применимы web-навыки; один UI для двух платформ; веб-сборку удобно отлаживать; нативные возможности доступны через плагины | Нужно самим проверять поведение WebView, клавиатуры, safe areas и жизненный цикл; качество нативного ощущения зависит от UI; плагины требуют проверки совместимости |
| Flutter | Подходит, если кастомная анимация/отрисовка или очень точное единое поведение станут приоритетом | Полный контроль отрисовки и единый UI; много готовых мобильных компонентов | Dart и новая экосистема; UI не переиспользует HTML/CSS; своя модель рендеринга и навигации |
| React Native | Подходит, если команда хочет JavaScript/React и UI на нативных компонентах | JavaScript/React; нативные платформенные компоненты и доступ к платформенным API | Нужны React/JSX и отдельная мобильная структура; UI не является HTML/CSS и не переиспользует существующие Blade-шаблоны напрямую; отдельная нативная сборочная цепочка |

Сравнение опирается на официальные описания [Capacitor](https://capacitorjs.com/docs), [Flutter](https://docs.flutter.dev/resources/architectural-overview) и [React Native](https://reactnative.dev/docs/intro-react). Решение можно пересмотреть по результатам прототипа на реальных устройствах. Не использовать WebGL/игровой движок без необходимости.

## Серверная схема

```text
Capacitor app (HTML/CSS/JS)
        │ HTTPS JSON API v1
        ▼
Laravel modular monolith ── Laravel Storage ── local disk / S3-compatible / CDN
   │             │
   ▼             ▼
 MySQL          Redis (rate limits/cache/queues when useful)
   │
   └── queue workers: image variants and non-critical analytics

Web-admin (Laravel web routes + Blade/AdminLTE already present in repo)
```

## Текущее состояние репозитория (аудит TASK-010)

- В репозитории Laravel 13/PHP 8.5.11 и Vite. Local/stage/prod используют PHP-FPM 8.5.11, Horizon/Supervisor — PHP CLI 8.5.11; CI также выполняется на PHP 8.5.11. `vite.config.js` собирает только существующие web assets; отдельный мобильный клиент и базовый API v1 находятся в `mobile/` и `routes/api.php`.
- В `mobile/` создан изолированный Capacitor 8 клиент на JavaScript/Vite; API base URL централизован в `mobile/src/config/api.js` и берётся только из `VITE_API_BASE_URL`. Native shells Android/iOS созданы; app ID пока временный `com.example.fourpictureoneword`.
- Уже настроены web-аутентификация, `User` с ролями Spatie и AdminLTE. Это существующий backend с пользовательскими функциями, поэтому игровые изменения должны добавляться отдельными миграциями и сохранять совместимость текущих пользователей/администраторов.
- `/` — публичный лендинг игры (`route('home')`), локализованные версии доступны по `/{locale}` для `ru`, `tj`, `en` (`route('home.locale')`); аутентификация не требуется, тексты лежат в `lang/{locale}/landing.php`, стили — в `resources/sass/landing.scss` и собираются отдельным Vite entry `landing.scss`.
- `/admin/dashboard` защищён web-аутентификацией и ролями `Admin`/`Super Admin`; `Moderator` и обычные зарегистрированные пользователи не имеют доступа. Публичная регистрация выключена, демо-учётки сидируются только в `local` и `testing`, а role seeder можно повторять.
- AdminLTE editor TASK-041 управляет только черновиками уровней и переводами; изменение уровня вместе с RU/TJ/EN ответами и буквенными плитками выполняется в одной транзакции. Опубликованный/архивный контент этим редактором не меняется.
- TASK-042 принимает только набор из четырёх JPEG/PNG/WebP изображений, проверяет фактическую декодируемость и размеры, сохраняет файлы в приватном `local` Storage с UUID-ключами и обновляет метаданные одной БД-транзакцией. При ошибке БД новые файлы удаляются; после успешной замены старые файлы очищаются.
- Для приватных изображений Laravel выдаёт временные подписанные `/storage/...` URL, проверяемые при каждом запросе. Nginx обрабатывает `/storage/` до общего regex статических изображений и передаёт запрос Laravel; без этого правила Nginx возвращал 404 до проверки подписи.
- TASK-043 ставит отдельный Horizon job на очередь `images` для каждого изображения. Worker создаёт private thumbnail (до 320×320) и display (до 1280×1280), сохраняет исходный формат и оставляет оригинал как fallback. Job retry идемпотентен по текущему storage key; устаревший job после замены источника ничего не сохраняет. Horizon timeout 75s находится между job timeout 60s и Redis retry_after 90s.
- TASK-044 переводит draft в published только после проверки активной и локализованной категории, всех обязательных переводов, правильного состава плиток и доступности четырёх оригиналов. Publish/archive транзакционно блокируют строку уровня; редактор и загрузчик повторно проверяют draft под той же блокировкой, чтобы параллельная операция не изменила опубликованный контент. Архивирование сохраняет строки уровня, изображения и историю прогресса.
- TASK-045 упорядочивает опубликованные уровни по `(sequence,id)`. Перемещение вверх/вниз блокирует список опубликованных уровней в транзакции, сначала переносит их на временный непересекающийся диапазон `sequence`, затем записывает плотный порядок `1..N`; tie-break по ID делает старые совпадающие значения детерминированными. Публикация/архивирование блокируют тот же набор строк перед изменением статуса.
- TASK-046 строит AdminLTE статистику агрегатным SQL по `level_id` (начала, завершения, ответы и подсказки) с пагинацией уровней. Персональные идентификаторы игроков не выбираются; отдельная статистическая таблица или миграция не нужны.
- Laravel Sanctum 4 установлен, его `personal_access_tokens` использует полиморфный `tokenable`, а `routes/api.php` обслуживает базовый `/api/v1/health`. Модели `Player` и `User` поддерживают Sanctum токены; bearer token восстанавливает owner через `tokenable`, поэтому для API-токенов Player отдельный provider/guard не нужен. Middleware `player` поверх `auth:sanctum` ограничивает игровые маршруты principal типа `Player`; в игровых контроллерах `auth()->user()`/`Request::user()` — текущий `Player`. Guest session endpoint реализован в TASK-030.
- `POST /api/v1/auth/guest` создаёт Player, его пустой кошелёк и bearer token в одной транзакции; публичный endpoint ограничен до 10 созданий в минуту на IP. `DELETE /api/v1/auth/session` отзывает только текущий Player token. Клиентское имя устройства сохраняется только как метка токена, не как идентификатор.
- Guest token не даёт доступ к игровым маршрутам как `User`: middleware отвергает principal неверного типа, а запросы без токена получают 401. `players.user_id` остаётся nullable; связь аккаунта позже обновит существующего Player и сохранит тот же `player_id` для прогресса, кошелька и остальных игровых данных. Автоматическое слияние двух Player не выполняется.
- API каталога локализует активные категории и только опубликованные полные уровни. Запросы eager-load-ят нужные переводы и картинки, cursor paginate по стабильному порядку; сериализатор использует grapheme count для `answer_length`, исключает правильный ответ и выдаёт подписанные 24-часовые URL для private storage.
- `GET /api/v1/progress` ограничен текущим Player, отдаёт страницу его записей и серверные статистику/баланс. Общий `CurrentLevelResolver` выбирает активную незавершённую задачу и используется также карточкой профиля.
- TASK-034 реализует `GET /api/v1/me` и `PATCH /api/v1/me/settings`; язык, звук, haptics и тема принадлежат текущему Player. Начальные значения: `ru`, звук включён, haptics включены, системная тема; сервер принимает только поддерживаемые локали и enum темы.
- В API v1 выделен именованный `game-api` rate limiter: 120 запросов в минуту на Player и 600 на IP для защищённых игровых маршрутов; создание guest session отдельно ограничено 10 запросами в минуту на IP. Аутентификация `Player` проверяется middleware до выполнения игрового API, а изменяющие профиль данные принимаются только после Form Request validation.
- `User` отвечает за существующую web-учётную запись с обязательными email/password. `Player` — отдельный игровой principal: гость создаётся без `User`, а `players.user_id` nullable и unique. Привязка зарегистрированного пользователя меняет FK у той же строки `players`, сохраняя `player.id` и весь игровой прогресс. Физический device ID не является идентичностью.
- Единый JSON envelope ошибок для `/api/*` зарегистрирован централизованно: validation, auth, authorization, not found, HTTP и server errors возвращают стабильные `message`, `code`, `errors`; детали 5xx скрыты. Web-исключения продолжают обрабатываться стандартно. Health endpoint возвращает `{"status":"ok"}`.
- Фактическая MySQL `users` совпадает с исходной миграцией: 9 колонок, обязательные уникальные email и пароль, без `preferred_locale`/`is_guest`. Таблицы `players`, `player_level_progress`, `player_wallets` и `wallet_transactions` описаны новыми миграциями и проверены SQLite feature-тестами; их применение в локальную MySQL ожидает доступности Docker.
- `User` содержит fillable-атрибуты, которых нет в фактической таблице `users` (например `block`, `avatar`, `nickname`, `country`, `timezone`). До разработки, использующей эти поля, проверить связанные функции приложения и решить, нужны ли отдельные миграции или модель очищается от устаревших атрибутов.
- MySQL/Redis определены в конфигурации и Compose; конфигурация также содержит ClickHouse и S3-compatible диски. Host приложения на локальной машине не видит внутреннее имя MySQL; Artisan команды для этой конфигурации запускаются внутри `php` контейнера.
- В PHP runtime local/stage/prod образов и CI включены `ext-intl` (ICU) и `mbstring`; Composer явно требует расширение для NFC нормализации таджикских/кириллических строк. Composer допускает PHP `^8.5`, Docker образы закреплены на 8.5.11.
- `AnswerNormalizer` сохраняет отображаемый ответ отдельно от Unicode-нормализованного ответа, сегментирует плитки по графемам и не применяет языковые правила, специфичные для русского.
- Старые миграции уже применены. Не редактировать их; игровые изменения вносить отдельными новыми миграциями.
- Локальные контейнеры MySQL и Redis healthy; Laravel успешно читает схему MySQL, а Predis ping возвращает `PONG`. Контейнеры работают, но Android/iOS native builds в этой среде не выполнялись.

Модули Laravel в одном приложении: Identity (`User` account и `Player` game principal), Catalog (уровни/категории/переводы), Gameplay (попытки/прогресс/подсказки), Wallet (ledger), Daily, Admin, Analytics adapter. Для analytics TASK-062 вводит интерфейс `AnalyticsProvider`, каталог `level_started`/`level_completed`/`hint_used` и log adapter на отдельный ротируемый канал. В события входят только ID уровня, поддерживаемая локаль и при использовании подсказки её тип; Player ID, IP, ответы и произвольные свойства исключены. HTTP-контроллеры валидируют и делегируют в небольшие actions/services; транзакционные правила находятся в прикладном слое, а не в Blade или UI-компонентах. Общие сервисы имеют ясные интерфейсы; отдельные микросервисы не нужны.

## Клиентские модули

- `screens`: home, level, categories, settings.
- `game`: состояние текущего ответа, выбор/снятие плиток, анимация результата.
- `api`: базовый URL по окружению, bearer token, таймауты, повтор только безопасных запросов.
- `storage`: локальный профиль/токен, кэш опубликованных уровней, незавершённый ввод и outbox идемпотентных действий.
- `i18n`: интерфейсные строки по locale; контент уровня приходит с сервера. Для сегментации и отображения использовать Unicode-совместимую обработку.
- `native`: изолированные адаптеры haptics, audio, status/navigation bars и app lifecycle.

TASK-050 подключает гостевую сессию через `POST /api/v1/auth/guest` и восстанавливает профиль через `GET /api/v1/me`. Bearer token хранится Android-плагином в AES-GCM зашифрованном SharedPreferences с ключом Android Keystore, а в iOS — в Keychain с атрибутом `ThisDeviceOnly`. В браузерной разработке token держится только в памяти процесса страницы. Выход сначала отзывает текущий серверный токен, затем удаляет локальную копию; после перезапуска приложение проверяет сохранённую сессию на сервере.

TASK-051 строит домашний экран по `GET /me` и `GET /progress`: баланс, доступный текущий уровень и серверная статистика. Действие продолжения получает локализованные данные уровня через `GET /levels/{level}`; уровень определяется серверным `current_level_id`, а при отсутствии доступных уровней действие выключено.

TASK-052 отображает четыре картинки, ответные позиции и выданные API плитки. В рамках TASK-087 админка требует ровно 12 Unicode-графем для каждого перевода, публикация проверяет покрытие ответа с кратностью, API перемешивает набор, а UI располагает плитки в 6×2 и адаптирует сетку к ширине экрана. Аудит MySQL нашёл один опубликованный уровень и три перевода с коротким набором; все исправлены и повторно проверены: 12 плиток, корректные одиночные графемы и покрытие ответа с учётом кратности. Выбор и снятие плиток меняют только локальный ввод; правильность, прогресс и баланс остаются серверными решениями. Пользовательские скриншоты — визуальный ориентир, а не макет для точного копирования.

TASK-053 отправляет полный ответ в `POST /levels/{level}/attempts` с `Idempotency-Key`. Повтор после неясного сетевого результата использует тот же ключ и тело; клиент блокирует правку ожидающего ответа. Серверные `correct`, награда, баланс и `next_level_id` определяют экран результата и переход.

TASK-054 вызывает hints API с намерением и `Idempotency-Key`; цены, проверка Coins и эффекты остаются на сервере. По TASK-089 кнопка `A` стоит 60 Coins и открывает одну первую слева закрытую букву; позицию нельзя передать с клиента. Баланс, открытые буквы и оставшиеся плитки клиент обновляет только из ответа сервера; `insufficient_coins` не меняет состояние.

Админская валидация уровней ограничивает каждый локализованный ответ значением `game.max_answer_graphemes` (12 Unicode grapheme clusters) и требует ровно 12 игровых плиток с полным покрытием ответа; обе проверки выполняются при сохранении и публикации. Длина считается по графемам, включая кириллические и таджикские буквы, а не по байтам/кодовым точкам.

Главный экран использует `GET /me.current_level_id` и `current_level_status` (`in_progress`, `available` или `null`): он показывает карточку именно выбранной сервером загадки с четырьмя кешируемыми изображениями и категорией. Незавершённый серверный прогресс или локальный черновик для того же Player/locale/content version показывает действие «Продолжить»; для следующего доступного уровня без ввода — «Играть». Когда уровень недоступен, приложение сохраняет рабочее состояние с пояснением вместо пустого экрана. Карточка и CTA не меняют серверный прогресс.

TASK-055 загружает каталоги по серверному locale и сохраняет языковые/звуковые настройки в профиле Player через `PATCH /me/settings`; фильтрация уровней и доступность локализованного контента остаются серверными.

Мобильные UI-строки должны храниться в централизованных locale-каталогах `ru`, `tj`, `en`; компоненты используют ключи/параметры, а не захардкоженный текст. Все состояния и accessibility labels переводятся. Переключение языка обновляет профиль и локализованный контент API. CI/тесты проверяют полноту каталога, и при выбранном `tj` запрещено молча показывать строки другого языка. Каждая новая страница/секция обязана поставлять переводы на все три языка (TASK-090).

TASK-056 задаёт safe-area insets для всех четырёх сторон, целевые размеры касаний, заметный keyboard focus, reduced-motion поведение и фокус заголовка после навигации для VoiceOver/TalkBack.

TASK-057 кэширует профиль, прогресс, списки и загруженные карточки уровня в IndexedDB без bearer token. При сетевой ошибке восстанавливает доступный кэш и незавершённый ответ; черновики изолированы по Player, locale и level и привязаны к `content_version`, а принятые сервером подсказки сохраняют обновлённые плитки. Завершённый ответ удаляет черновик. После изменения locale клиент перечитывает `/me`, чтобы использовать вычисленный сервером `current_level_id`. Кэшированные карточки содержат URL изображений, которые для private storage могут истечь через 24 часа; серверный запрос потребуется для их обновления.

TASK-058 сохраняет одну ожидающую игровую операцию (ответ или подсказку) вместе с исходными locale/body и `Idempotency-Key` в локальном кэше до запроса. При восстановлении предлагает открыть исходный уровень и повторить ту же операцию; очередь очищается после ответа сервера, отклонения валидации или выхода и удаляется после 30 дней в соответствии с серверным сроком idempotency-записей. Это безопасный повтор действия, не автономная очередь начисления Coins.

TASK-086 завершена: `GET /me` возвращает `current_level_status` (`in_progress`, `available`, `null`), а мобильный главный экран показывает карточку `current_level_id` с категорией и четырьмя изображениями. Серверный незавершённый прогресс или локальный черновик того же Player/locale/content version предлагают «Продолжить»; следующий уровень без начатого ввода предлагает «Играть». Ограничения ответа и плиток отслеживаются в TASK-087/088; цена и UI `reveal_letter` — в TASK-089.

TASK-089 устанавливает цену `reveal_letter` в 60 Coins в серверном `config/game.php`. На мобильном игровом экране рядом с сеткой плиток находится кнопка `A` с показанной ценой. Клиент отправляет только тип подсказки и idempotency key; сервер атомарно списывает цену и открывает первую незакрытую позицию слева. Ответ API подтверждает баланс и позицию; недостаток Coins не меняет прогресс или кошелёк.

TASK-090 хранит весь мобильный UI-текст в `mobile/src/i18n/catalogs.js`; `setLocale` синхронизирует выбранный языковой код HTML-документа и заголовок. Переводы ru/tj/en обязаны иметь одинаковые ключи и interpolation placeholders. `t()` бросает ошибку при отсутствующем ключе/языке, а API errors отображаются через локальный кодовый адаптер, без показа серверной англоязычной строки. Любой новый экран, состояние, доступное имя или ошибка должны использовать `t()` и дополнять все три каталога в той же задаче; Node tests проверяют покрытие и неиспользуемые ключи.

URL API задаётся конфигурацией окружения сборки, а не зашивается в игровую логику. Секреты в приложении не размещаются.

В mobile Vite-клиенте разрешено передавать в `VITE_*` только публичную конфигурацию (например, адрес API): Vite встраивает такие значения в клиентский bundle. API ключи и другие секреты там не хранить.

## Unicode и ответ

Сервер хранит исходное отображение и нормализованное значение. `AnswerNormalizer` применяет Unicode NFC, полное Unicode case folding и NFC повторно; обрезает пробелы только по краям, не меняя внутренние символы. Ответы передаются целой строкой UTF-8; набор плиток сегментируется по графемам через Unicode `\\X`. Это общая Unicode-обработка, без русской транслитерации или языковой подмены букв. Уникальные таджикские буквы сохраняются.

## Игровое состояние и доверие

Сервер — источник истины для правильности, прогресса и монет. Владелец этих данных — `Player`, независимо от наличия связанного `User`. Клиент может подделать локальное состояние, поэтому завершение уровня вычисляется сервером из отправленного предположения и ответа уровня. Уровень постепенно выдаётся API; правильное решение не включается в ответ. Это не защищает от клиента, который перебирает ответы: применяются throttling, лимит частоты попыток и идемпотентная выдача награды. Для особо ценной экономики потребуется оценить усиленную выдачу контента/anti-cheat отдельно.

Изменение прогресса и кошелька проводится транзакционно с блокировкой строки `Player` и кошелька. Строка Player сериализует операции даже когда progress row ещё не существует; уникальность `(player_id, level_id)` остаётся последней защитой. Клиент передаёт `Idempotency-Key` для попытки и подсказки. Игровой эффект, ledger, баланс и сохранённые HTTP status/body фиксируются одной транзакцией; одинаковый ключ с тем же запросом не выполняет callback повторно, а возвращает записанный результат. Незавершённые записи без `completed_at` дают in-progress конфликт и не затрагиваются очисткой.

Единственная игровая валюта MVP — Coins. Стартовый баланс (+300), rewards (+10 за правильный ответ, +50 за завершение, milestones 50/100/500/1000: +150/+300/+300/+500, daily +100, streak 5/10: +20/+50, rewarded ad +50 с лимитом 5/сутки) и цены hints (30/40/100) хранятся в `config/game.php`. TASK-032/033 реализуют гостевой бонус, попытки, milestones и три подсказки. Daily, streak и рекламная выдача остаются отдельными задачами и обязаны проходить через тот же серверный wallet manager после своей авторизации/проверки источника.

Завершённые idempotency результаты хранятся 30 дней от `completed_at`. Плановая ежедневная очистка удаляет только завершённые записи старше этого срока пакетами; offline retry с исходным ключом гарантированно воспроизводит ответ в течение 30 дней. Решение записано в ADR-002.

## Offline и синхронизация

MVP кэширует полученный контент и локальные выбранные плитки; текущий уровень можно открыть без сети, но ответ и награда подтверждаются только сервером. Подсказки и завершение без сети не применяются к локальной экономике. После восстановления сети outbox отправляет те же операции с теми же ключами; конфликты разрешаются серверным состоянием. При повторе завершённого уровня сервер возвращает уже достигнутый результат без повторной награды. Это намеренно проще полной офлайн-экономики.

## Изображения, кэш и фоновые задачи

В БД хранятся storage key, порядок и метаданные, не бинарные данные. Laravel Storage скрывает провайдера. Загрузка проверяет MIME/размер/разрешение, преобразования изображений выполняются очередью. API кэширует опубликованный контент с версией/ETag; приватный прогресс не кладётся в общий HTTP-кэш. CDN подключается перед объектным хранилищем при росте трафика. Redis применяется к rate limiting, короткому кэшу и очередям; критические балансовые данные всегда в MySQL.

## Админ-панель

Использовать существующий web стек Laravel/Blade и установленный AdminLTE, если аудит подтвердит пригодность. Права администраторов назначать через существующую систему ролей. Проверка публикации обязательна: активная категория, ровно четыре активных изображения, заполненные переводы и валидный набор плиток. Изменение уже опубликованного контента не должно менять историю начисления вознаграждений.

## Рост функциональности

Ежедневные задания, достижения, рейтинг, рекламные показы и покупки добавляются отдельными модулями и таблицами только при старте соответствующих фаз. Рекламный и платёжный провайдеры подключаются адаптерами; подтверждение покупок выполняет backend с проверкой receipt/webhook платформы. Аналитика публикует внутренние события через интерфейс, конкретный поставщик выбирается позже.
