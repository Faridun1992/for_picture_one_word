# Архитектура

Статус: архитектура MVP утверждена; базовый мобильный клиент, API каркас и первые таблицы реализованы по TASKS.md.

## Решение по клиенту

Рекомендуемый MVP: отдельный web-first клиент на HTML/CSS/TypeScript (или JavaScript с проверкой типов по мере роста) внутри Capacitor. Не превращать существующий Laravel Blade-сайт в игровую WebView-страницу: мобильный клиент должен быть отдельным приложением с собственными экранами, состоянием и API-клиентом. Это сохраняет навыки владельца и позволяет получить сборки Android/iOS с доступом к native API через плагины.

| Подход | Подходит игре | Сильные стороны | Издержки |
|---|---|---|---|
| Capacitor + HTML/CSS/JS | Игровой цикл — формы, изображения, анимации и простые касания; нагрузки на GPU невысоки | Максимально применимы web-навыки; один UI для двух платформ; веб-сборку удобно отлаживать; нативные возможности доступны через плагины | Нужно самим проверять поведение WebView, клавиатуры, safe areas и жизненный цикл; качество нативного ощущения зависит от UI; плагины требуют проверки совместимости |
| Flutter | Подходит, если кастомная анимация/отрисовка или очень точное единое поведение станут приоритетом | Полный контроль отрисовки и единый UI; много готовых мобильных компонентов | Dart и новая экосистема; UI не переиспользует HTML/CSS; своя модель рендеринга и навигации |
| React Native | Подходит, если команда хочет JavaScript/React и UI на нативных компонентах | JavaScript/React; нативные платформенные компоненты и доступ к платформенным API | Нужны React/JSX и отдельная мобильная структура; UI не является HTML/CSS и не переиспользует существующие Blade-шаблоны напрямую; отдельная нативная сборочная цепочка |

Сравнение опирается на официальные описания [Capacitor](https://capacitorjs.com/docs), [Flutter](https://docs.flutter.dev/resources/architectural-overview) и [React Native](https://reactnative.dev/docs/intro-react). Решение можно пересмотреть по результатам прототипа на реальных устройствах. Не использовать WebGL/игровой движок без необходимости.

## Серверная схема

```text
Capacitor app (HTML/CSS/JS)
        │ HTTPS JSON API v1
        ▼
Laravel modular monolith ── Laravel Storage ── local disk / S3-compatible / CDN
   │             │
   ▼             ▼
 MySQL          Redis (rate limits/cache/queues when useful)
   │
   └── queue workers: image variants and non-critical analytics

Web-admin (Laravel web routes + Blade/AdminLTE already present in repo)
```

## Текущее состояние репозитория (аудит TASK-010)

- В репозитории Laravel 13/PHP 8.4 и Vite. `vite.config.js` собирает только существующие web assets; отдельный мобильный клиент и базовый API v1 находятся в `mobile/` и `routes/api.php`.
- В `mobile/` создан изолированный Capacitor 8 клиент на JavaScript/Vite; API base URL централизован в `mobile/src/config/api.js` и берётся только из `VITE_API_BASE_URL`. Native shells Android/iOS созданы; app ID пока временный `com.example.fourpictureoneword`.
- Уже настроены web-аутентификация, `User` с ролями Spatie и AdminLTE. Это существующий backend с пользовательскими функциями, поэтому игровые изменения должны добавляться отдельными миграциями и сохранять совместимость текущих пользователей/администраторов.
- Laravel Sanctum 4 установлен, его `personal_access_tokens` использует полиморфный `tokenable`, а `routes/api.php` обслуживает базовый `/api/v1/health`. Модели `Player` и `User` поддерживают Sanctum токены; bearer token восстанавливает owner через `tokenable`, поэтому для API-токенов Player отдельный provider/guard не нужен. Middleware `player` поверх `auth:sanctum` ограничивает игровые маршруты principal типа `Player`; в игровых контроллерах `auth()->user()`/`Request::user()` — текущий `Player`. Guest session endpoint реализован в TASK-030.
- `POST /api/v1/auth/guest` создаёт Player, его пустой кошелёк и bearer token в одной транзакции; публичный endpoint ограничен до 10 созданий в минуту на IP. `DELETE /api/v1/auth/session` отзывает только текущий Player token. Клиентское имя устройства сохраняется только как метка токена, не как идентификатор.
- Guest token не даёт доступ к игровым маршрутам как `User`: middleware отвергает principal неверного типа, а запросы без токена получают 401. `players.user_id` остаётся nullable; связь аккаунта позже обновит существующего Player и сохранит тот же `player_id` для прогресса, кошелька и остальных игровых данных. Автоматическое слияние двух Player не выполняется.
- API каталога локализует активные категории и только опубликованные полные уровни. Запросы eager-load-ят нужные переводы и картинки, cursor paginate по стабильному порядку; сериализатор использует grapheme count для `answer_length`, исключает правильный ответ и выдаёт подписанные 24-часовые URL для private storage.
- `GET /api/v1/progress` ограничен текущим Player, отдаёт страницу его записей и серверные статистику/баланс. Общий `CurrentLevelResolver` выбирает активную незавершённую задачу и используется также карточкой профиля.
- TASK-034 реализует `GET /api/v1/me` и `PATCH /api/v1/me/settings`; язык, звук, haptics и тема принадлежат текущему Player. Начальные значения: `ru`, звук включён, haptics включены, системная тема; сервер принимает только поддерживаемые локали и enum темы.
- В API v1 выделен именованный `game-api` rate limiter: 120 запросов в минуту на Player и 600 на IP для защищённых игровых маршрутов; создание guest session отдельно ограничено 10 запросами в минуту на IP. Аутентификация `Player` проверяется middleware до выполнения игрового API, а изменяющие профиль данные принимаются только после Form Request validation.
- `User` отвечает за существующую web-учётную запись с обязательными email/password. `Player` — отдельный игровой principal: гость создаётся без `User`, а `players.user_id` nullable и unique. Привязка зарегистрированного пользователя меняет FK у той же строки `players`, сохраняя `player.id` и весь игровой прогресс. Физический device ID не является идентичностью.
- Единый JSON envelope ошибок для `/api/*` зарегистрирован централизованно: validation, auth, authorization, not found, HTTP и server errors возвращают стабильные `message`, `code`, `errors`; детали 5xx скрыты. Web-исключения продолжают обрабатываться стандартно. Health endpoint возвращает `{"status":"ok"}`.
- Фактическая MySQL `users` совпадает с исходной миграцией: 9 колонок, обязательные уникальные email и пароль, без `preferred_locale`/`is_guest`. Таблицы `players`, `player_level_progress`, `player_wallets` и `wallet_transactions` описаны новыми миграциями и проверены SQLite feature-тестами; их применение в локальную MySQL ожидает доступности Docker.
- `User` содержит fillable-атрибуты, которых нет в фактической таблице `users` (например `block`, `avatar`, `nickname`, `country`, `timezone`). До разработки, использующей эти поля, проверить связанные функции приложения и решить, нужны ли отдельные миграции или модель очищается от устаревших атрибутов.
- MySQL/Redis определены в конфигурации и Compose; конфигурация также содержит ClickHouse и S3-compatible диски. Host приложения на локальной машине не видит внутреннее имя MySQL; Artisan команды для этой конфигурации запускаются внутри `php` контейнера.
- В PHP runtime local/stage/prod образов включён `ext-intl` (ICU) вместе с `mbstring`; Composer явно требует расширение для NFC нормализации таджикских/кириллических строк.
- `AnswerNormalizer` сохраняет отображаемый ответ отдельно от Unicode-нормализованного ответа, сегментирует плитки по графемам и не применяет языковые правила, специфичные для русского.
- Старые миграции уже применены. Не редактировать их; игровые изменения вносить отдельными новыми миграциями.
- Локальные контейнеры MySQL и Redis healthy; Laravel успешно читает схему MySQL, а Predis ping возвращает `PONG`. Контейнеры работают, но Android/iOS native builds в этой среде не выполнялись.

Модули Laravel в одном приложении: Identity (`User` account и `Player` game principal), Catalog (уровни/категории/переводы), Gameplay (попытки/прогресс/подсказки), Wallet (ledger), Daily, Admin, Analytics adapter. HTTP-контроллеры валидируют и делегируют в небольшие actions/services; транзакционные правила находятся в прикладном слое, а не в Blade или UI-компонентах. Общие сервисы имеют ясные интерфейсы; отдельные микросервисы не нужны.

## Клиентские модули

- `screens`: home, level, categories, settings.
- `game`: состояние текущего ответа, выбор/снятие плиток, анимация результата.
- `api`: базовый URL по окружению, bearer token, таймауты, повтор только безопасных запросов.
- `storage`: локальный профиль/токен, кэш опубликованных уровней, незавершённый ввод и outbox идемпотентных действий.
- `i18n`: интерфейсные строки по locale; контент уровня приходит с сервера. Для сегментации и отображения использовать Unicode-совместимую обработку.
- `native`: изолированные адаптеры haptics, audio, status/navigation bars и app lifecycle.

URL API задаётся конфигурацией окружения сборки, а не зашивается в игровую логику. Секреты в приложении не размещаются.

В mobile Vite-клиенте разрешено передавать в `VITE_*` только публичную конфигурацию (например, адрес API): Vite встраивает такие значения в клиентский bundle. API ключи и другие секреты там не хранить.

## Unicode и ответ

Сервер хранит исходное отображение и нормализованное значение. `AnswerNormalizer` применяет Unicode NFC, полное Unicode case folding и NFC повторно; обрезает пробелы только по краям, не меняя внутренние символы. Ответы передаются целой строкой UTF-8; набор плиток сегментируется по графемам через Unicode `\\X`. Это общая Unicode-обработка, без русской транслитерации или языковой подмены букв. Уникальные таджикские буквы сохраняются.

## Игровое состояние и доверие

Сервер — источник истины для правильности, прогресса и монет. Владелец этих данных — `Player`, независимо от наличия связанного `User`. Клиент может подделать локальное состояние, поэтому завершение уровня вычисляется сервером из отправленного предположения и ответа уровня. Уровень постепенно выдаётся API; правильное решение не включается в ответ. Это не защищает от клиента, который перебирает ответы: применяются throttling, лимит частоты попыток и идемпотентная выдача награды. Для особо ценной экономики потребуется оценить усиленную выдачу контента/anti-cheat отдельно.

Изменение прогресса и кошелька проводится транзакционно с блокировкой соответствующих записей и уникальными ключами операций. Клиент передаёт `Idempotency-Key` для завершения и подсказки. Игровой эффект и сохранённые HTTP status/body фиксируются одной транзакцией; одинаковый ключ с тем же запросом не выполняет callback повторно, а возвращает записанный результат. Незавершённые записи без `completed_at` дают in-progress конфликт и не затрагиваются очисткой.

Завершённые idempotency результаты хранятся 30 дней от `completed_at`. Плановая ежедневная очистка удаляет только завершённые записи старше этого срока пакетами; offline retry с исходным ключом гарантированно воспроизводит ответ в течение 30 дней. Решение записано в ADR-002.

## Offline и синхронизация

MVP кэширует полученный контент и локальные выбранные плитки; текущий уровень можно открыть без сети, но ответ и награда подтверждаются только сервером. Подсказки и завершение без сети не применяются к локальной экономике. После восстановления сети outbox отправляет те же операции с теми же ключами; конфликты разрешаются серверным состоянием. При повторе завершённого уровня сервер возвращает уже достигнутый результат без повторной награды. Это намеренно проще полной офлайн-экономики.

## Изображения, кэш и фоновые задачи

В БД хранятся storage key, порядок и метаданные, не бинарные данные. Laravel Storage скрывает провайдера. Загрузка проверяет MIME/размер/разрешение, преобразования изображений выполняются очередью. API кэширует опубликованный контент с версией/ETag; приватный прогресс не кладётся в общий HTTP-кэш. CDN подключается перед объектным хранилищем при росте трафика. Redis применяется к rate limiting, короткому кэшу и очередям; критические балансовые данные всегда в MySQL.

## Админ-панель

Использовать существующий web стек Laravel/Blade и установленный AdminLTE, если аудит подтвердит пригодность. Права администраторов назначать через существующую систему ролей. Проверка публикации обязательна: активная категория, ровно четыре активных изображения, заполненные переводы и валидный набор плиток. Изменение уже опубликованного контента не должно менять историю начисления вознаграждений.

## Рост функциональности

Ежедневные задания, достижения, рейтинг, рекламные показы и покупки добавляются отдельными модулями и таблицами только при старте соответствующих фаз. Рекламный и платёжный провайдеры подключаются адаптерами; подтверждение покупок выполняет backend с проверкой receipt/webhook платформы. Аналитика публикует внутренние события через интерфейс, конкретный поставщик выбирается позже.
