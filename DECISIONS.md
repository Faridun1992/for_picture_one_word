# Decisions

Здесь фиксируются принятые архитектурные решения. Требования и текущее выполнение остаются в `PROJECT_SPEC.md` и `TASKS.md`.

## ADR-001 — Разделить игрового игрока и web-учётную запись

- **Статус:** принято
- **Дата:** 2026-09-27
- **Контекст:** существующая таблица `users` требует email и password и обслуживает web-аутентификацию. Гость должен играть без регистрации, а позднее иметь возможность связать игровой профиль с зарегистрированным аккаунтом.
- **Решение:** создать отдельную сущность `players`. `users` остаётся учётной записью. Гостевой `Player` не создаёт строку `users` и не получает фиктивные email/password. `players.user_id` nullable и unique; физический device ID не используется как единственная идентичность.
- **Связь аккаунта:** при привязке обновляется `user_id` существующего `Player`; `player.id` остаётся прежним, поэтому прогресс, кошелёк и история продолжают ссылаться на тот же профиль. Если у аккаунта уже есть другой `Player`, linking должен завершаться безопасным конфликтом до появления отдельной стратегии объединения; автоматическое слияние данных запрещено.
- **Аутентификация:** мобильный guest token выдаётся `Player` через установленный Sanctum и polymorphic `personal_access_tokens`. Sanctum bearer-token guard восстанавливает модель-владельца через `tokenable`, отдельный provider/guard для API-токенов не требуется; `auth:sanctum` вместе с middleware `player` оставляет `auth()->user()` типом `Player` на игровых маршрутах. Web session продолжает использовать `User`. Игровые API должны разрешать только principal типа `Player`; токен `User` не даёт доступа к ним.
- **Удаление аккаунта:** FK `players.user_id` использует `ON DELETE SET NULL`, чтобы удаление `User` не удаляло игровой профиль и его прогресс.
- **Последствия:** `player_level_progress`, `player_wallets`, `wallet_transactions` и `idempotency_requests` принадлежат `player_id`. Не менять `users.email/password` и не редактировать уже применённые миграции; таблицу `players` создавать новой миграцией.
- **Реализация:** TASK-020 и TASK-030. Гостевая сессия создаёт `Player` с nullable `user_id`, выпускает его Sanctum token и не создаёт `User`; удаление токена ограничено текущим Player token. Связывание аккаунта сохраняет существующую игровую сущность и её данные. Зависимые задачи: TASK-025/026/027.

## ADR-002 — Хранить завершённые Idempotency-Key результаты 30 дней

- **Статус:** принято
- **Дата:** 2026-09-27
- **Контекст:** мобильный клиент может повторить запрос после offline-режима, таймаута или потери ответа. Повторное применение завершения уровня/подсказки способно повторно изменить прогресс или баланс.
- **Решение:** на один `(player_id, key)` хранить canonical hash запроса, operation и итоговые HTTP status/body. После успешного завершения задавать `completed_at`; результат хранить 30 дней с этого момента. Тот же ключ, операция и запрос в этом сроке возвращают сохранённый результат без исполнения игровой операции; несовпадающая операция/тело дают 409. Незавершённая запись не истекает и не удаляется по TTL до финального статуса. После 30 дней завершённые записи разрешено удалять или архивировать.
- **Реализация:** TASK-027: атомарный executor, уникальность `(player_id, key)`, ежедневная пакетная очистка завершённых результатов и feature-тесты replay/conflict/rollback/retention.

## ADR-003 — Ограничить ответы 12 графемами и использовать 12 буквенных плиток

- **Статус:** принято
- **Дата:** 2026-10-03
- **Контекст:** игровое поле на телефоне должно сохранять компактную и предсказуемую компоновку; пользовательские референсы показывают 12 плиток и отдельную кнопку подсказки.
- **Решение:** каждый локализованный ответ содержит максимум 12 Unicode grapheme clusters. Набор содержит ровно 12 плиток: графемы ответа с правильной кратностью плюс дополнительные отвлекающие плитки, задаваемые администратором. Для ответа длиной 12 графем дополнительные плитки не задаются. UI перемешивает/показывает набор ориентировочно как 6×2; backend остаётся источником плиток.
- **Подсказка:** `reveal_letter` стоит 60 Coins за одну букву и открывает первую слева ещё не открытую позицию. Сервер выбирает позицию; списание/эффект атомарны и идемпотентны, при недостатке Coins состояние не меняется. Цена видна на кнопке `A`.
- **Главный экран:** если есть текущая незавершённая загадка, показывать её как основную карточку и действие «Продолжить»; иначе — следующий доступный уровень и «Играть». Черновик ввода локален и восстанавливается только при совпадении Player, locale и content version.
- **Визуальное направление:** референсы определяют композицию/иерархию, но не копируются буквально; сохраняются responsive layout, safe areas, контраст и доступность.
- **Последствия:** изменения поверх завершённых TASK-041/044/052/054 выполняются отдельными задачами TASK-087–089; данные/реализация считаются обновлёнными после миграции контента и прохождения тестов.

## ADR-004 — Требовать полные переводы мобильного UI на все поддерживаемые языки

- **Статус:** принято
- **Дата:** 2026-10-03
- **Контекст:** пользователь ожидает, что при выборе русского интерфейс полностью будет русским, а при выборе таджикского — таджикским. Частично переведённые экраны или незаметный fallback нарушают это требование.
- **Решение:** хранить UI strings в централизованных locale-каталогах `ru`, `tj`, `en`. Каждый новый экран/раздел/состояние добавляет переводы сразу для всех трёх языков; completeness проверяется автоматически/тестами. При выбранной locale запрещён silent fallback на другой язык. Динамический игровой контент должен загружаться API на выбранной locale.
- **Реализация:** задача TASK-090 добавляет/аудирует locale-каталоги, покрытие всех мобильных экранов и тест отсутствующих/лишних ключей.

## ADR-005 — Разместить публичный лендинг на `/`, а админку на `/admin/dashboard`

- **Статус:** принято
- **Дата:** 2026-10-03
- **Контекст:** раньше `route('home')` указывал на `/home` и открывал AdminLTE dashboard, доступный только ролям `Admin`/`Super Admin` (TASK-040). Для публичного промо-сайта игры такой маршрут неудобен: `/home` не выражает назначение, а главная страница закрыта авторизацией.
- **Решение:** `/` (`route('home')`) — публичный лендинг без аутентификации; локализованные версии доступны по `/{locale}` (`route('home.locale')`) с ограничением на `game.supported_locales`, остальные значения дают 404. Локали выбираются сегментом URL, а не только заголовком, чтобы каждая версия имела собственный адрес и `hreflang`. AdminLTE dashboard переносится на `/admin/dashboard` (`route('admin.dashboard')`), редиректы аутентификации и `config/adminlte.php` обновляются; старый `/home` больше не маршрутизируется, чтобы не держать второй публичный вход в админку.
- **Реализация:** задача TASK-091 добавляет `LandingController`, `resources/views/landing/index.blade.php`, `resources/sass/landing/`, locale-каталоги `lang/{locale}/landing.php`, отдельный Vite entry и тесты `LandingPageTest`/`LandingLocaleCatalogTest`; доступ админки проверяется в `AdminAccessTest`.
- **Последствия:** любые внешние ссылки на `/home` перестают работать и должны указывать на `/admin/dashboard`; при необходимости понадобится явный редирект со старого адреса.
